# Enterprise API & Application Performance Monitoring (APM) System

A working reference implementation matching the five-component design:
monitoring engine, data collection layer, database, web dashboard, and
alert/notification service.

## Project structure

```
apm_system/
├── app/
│   ├── main.py         # FastAPI app: REST API + dashboard serving
│   ├── monitoring.py   # Monitoring engine + data collection (probes, scheduler)
│   ├── alerts.py       # Alert & notification service (email + Teams)
│   ├── models.py       # Database schema (SQLAlchemy ORM)
│   ├── schemas.py      # API request/response validation
│   └── database.py     # DB connection (SQLite by default)
├── static/
│   └── index.html      # Web dashboard (status grid, chart, alert log)
├── seed_endpoints.py   # Registers sample endpoints for a quick test
├── requirements.txt
└── README.md
```

## 1. Setup

```bash
cd apm_system
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## 2. Run

```bash
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

Open the dashboard: **http://localhost:8000**
Interactive API docs (auto-generated by FastAPI): **http://localhost:8000/docs**

The database file `apm_system.db` (SQLite) is created automatically on
first run — no separate DB server needed to try it out.

## 3. Register endpoints to monitor

Either use the interactive docs at `/docs` → `POST /api/endpoints`, or run
the seed script for instant sample data:

```bash
python seed_endpoints.py
```

This registers three public test targets (a normal endpoint, a slow one,
and one that always returns HTTP 500) so you can see the dashboard,
charts and alerts populate within a minute of starting the server.

Example payload for registering your own endpoint:
```json
{
  "name": "Customer Orders API",
  "url": "https://internal.company.com/api/orders/health",
  "environment": "production-IIS",
  "check_interval_seconds": 30,
  "timeout_seconds": 5,
  "response_time_warn_ms": 800,
  "response_time_critical_ms": 2000,
  "consecutive_failures_for_alert": 2
}
```

## 4. Switching the database (SQL Server / PostgreSQL)

By default the app uses SQLite. To point it at a real enterprise database
instead, set the `DATABASE_URL` environment variable before starting:

```bash
# PostgreSQL
export DATABASE_URL="postgresql+psycopg2://user:password@localhost:5432/apm_db"
pip install psycopg2-binary

# SQL Server (via ODBC)
export DATABASE_URL="mssql+pyodbc://user:password@your_dsn_name"
pip install pyodbc
```

No code changes needed — SQLAlchemy handles the dialect switch.

## 5. Configuring alerts (email / Microsoft Teams)

Set these environment variables before starting the server:

```bash
# Email (SMTP)
export SMTP_HOST="smtp.office365.com"
export SMTP_PORT=587
export SMTP_USER="apm-alerts@yourcompany.com"
export SMTP_PASSWORD="your-app-password"
export ALERT_EMAIL_TO="ops-team@yourcompany.com,manager@yourcompany.com"

# Microsoft Teams (Incoming Webhook)
export TEAMS_WEBHOOK_URL="https://yourcompany.webhook.office.com/webhookb2/..."
```

To get a Teams webhook URL: open the target Teams channel → **Connectors**
(or **Workflows** in newer Teams) → **Incoming Webhook** → configure and
copy the generated URL.

If these variables aren't set, alerts are simply logged to the console
instead of sent — useful for local testing without spamming real channels.

## 6. Testing the failure scenarios (for your evaluation chapter)

| Scenario | How to simulate with this system |
|---|---|
| Normal operation | Register a healthy endpoint, observe steady "up" status |
| API unavailable | Register an endpoint pointing at a stopped service, or use `https://httpbin.org/status/503` |
| Elevated response time | Use `https://httpbin.org/delay/3` with a low `response_time_warn_ms` |
| HTTP 500 errors | Use `https://httpbin.org/status/500` |
| App pool failure (IIS) | Requires a small Windows-side agent (see "Extending" below) |
| Server unavailable | Point an endpoint at an unreachable host/port to trigger connection-error handling |
| Network interruption | Block the target with a local firewall rule mid-test |

For each scenario, capture: time of failure injection (from your test log)
vs. `triggered_at` timestamp on the resulting row in `/api/alerts` — that
difference is your **alert detection time** metric.

## 7. Extending to IIS application-pool checks

HTTP probing alone can't see IIS app-pool state. Add a small PowerShell-based
local agent on the Windows server that exposes app-pool status as JSON, e.g.:

```powershell
Import-Module WebAdministration
Get-WebAppPoolState -Name "YourAppPool" | ConvertTo-Json
```

Wrap that in a minimal local HTTP endpoint (or run it over WinRM/PowerShell
remoting from the monitoring engine), then register it in this system just
like any other endpoint — the monitoring engine already treats "endpoint
returns non-2xx or times out" as a failure condition.

## 8. Production notes

- Run behind a process manager (systemd service, or `pm2`/`supervisor`) so
  the scheduler survives reboots.
- Put FastAPI behind a reverse proxy (nginx) with HTTPS in production.
- Add authentication to the dashboard/API before exposing it beyond localhost.
- Schedule `monitoring.cleanup_old_results()` periodically if you want
  automatic retention/purging of old monitoring records.
